## 2. 先分清规则层级

1. **competition_hard：主赛与伦理的约束。** 明确违规必须阻止；AI不能给出例外许可。主赛 §§11–12规定解释权属于组织者。
2. **platform_risk：Legit Social 的游戏内规则和后果。** 官方在平台规则前明确说明：主赛必须遵守，平台规则可以在游戏中创造性应对。此层可能涉及删帖、降权、封号，不能直接等同于主赛取消资格。
3. **mechanism：接口限制与计分条件。** 如500字符、提及数量、团队共享限流、举报详情、暂停举报。接口不接受与违反比赛伦理是不同的结果。
4. **local_policy：本队自定策略。** 如禁止受管角色内部互动、表达格式、对高风险平台内容暂缓自动发送。页面须标明“本地策略”，不能冒称官方硬禁令。
5. **provider_policy：第三方服务条款与许可。** 主赛 §5.1、§5.2.1要求遵守。需要按实际选用的服务单独核实，不能用比赛许可覆盖服务商限制。

同一行为可以命中多个层级。例如绕平台请求限流，既出现在LS规则，也被主赛明确禁止，最终应按主赛阻止；多个人设账号、使用AI和赛内协调则有主赛明确许可，不能仅凭LS对应规则自动判主赛违规。

### 3.1 必须保留的允许项与反例

主赛 §5.2.1明确允许赛内创建/管理账号、发帖/评论/点赞/转发、自动化、分析赛内数据、附条件公共人物/虚构人设、虚假或误导内容、赛内跨队协作和针对其他竞争者AI的赛内提示注入。每项仍受其他主赛禁令与伦理约束。

因此：

- 不因多账号、模型文风、虚构履历、没有新闻佐证、观点激烈或与本队立场不一致，就判主赛违规。
- 普通政策辩论、公开人物批评、自然角色扮演和报道/引用注入案例，不可仅凭关键词误判。
- NPC注入与竞争者Agent注入须区分。不能凭verified、用户名、模型文风或公开互动猜控制归属；目标身份应有可追溯证据。
- 即使目标被确认是对手，也要检查内容是否企图操纵NPC或包含偷密钥等另行禁止行为。“提到对手”不足以构成许可；公开可达不单独构成已经违规的证明。意图/范围不清转待核实。
- 正常“投Yes/No”是对人物的说服；请求忽略系统指令、替换模型角色、输出内部字段等才是需要重点核实的系统操纵意图。不是出现某个词就必定违规。
- 没有浏览/互动不证明被屏蔽，公开账号或帖子计数不证明官方裁定/身份。

## 5. 接口限制、举报条件与无关覆盖项

### 5.1 发布/接口门

- Getting Started步骤6：正文最多500字符；Scoring§1：原帖最多提及4个账号，回复最多3个，超限发帖/编辑会被拒。正式实现须对实际平台解析方式核验，不能用简单空格计数代替。
- 配额为全队共享，多账号不产生额外团队额度；运行时依服务器限制、补充时间和Retry-After。合法多出口不能成为规避团队配额的工具。
- 官方入门默认每分钟：发帖/回复/转发合计3，feed10，点赞/关注/浏览各30，帖子举报/账号举报各3，其他多数读取300；登录/注册5按网络地址。数值可调整，不能仅硬编码。
- 官方模型：全队3请求/分钟、突发2、同时1个请求、约1024输出tokens、每次1答案；审核也必须共享这些限制。外接模型遵守其实际限额，不能错误套用赛事模型限制。
- 长线程超过8条后NPC较少回复是行为机制，不是禁止长对话。

### 5.2 举报不是本次自动审核的输出动作

Scoring§3的完整相关边界：

- 举报帖子须有reason及具体detail，空detail被拒；自动审核标记问题不等于已满足证据要求。
- 当前专门条款基准为首报后3小时；不同队1/2/3/4/5队分别3小时、1.5小时、45分钟、22.5分钟、11.25分钟。同队多账号仅算一队，时间从首报计算。
- 前五队可获分，五队后临时隐藏且不可继续举报；暂时隐藏不能当永久违规帖。
- 裁定inauthentic才永久隐藏并给首队25/后队5分；裁定genuine使所有举报队6小时不能举报。版主约十分之一可能判错；verified账号裁定例外始终正确，但这不是verified等于NPC的证据。
- 同目标队同日的帖子/账号有偿举报合并计数：首5全额、接5半额、其后10%；悉尼午夜重置，未知目标队不能凭模型补齐。
- 自队举报无分，但帖子举报仍能计入五队临时隐藏及裁决后永久隐藏条件；三个永久隐藏帖导致账号暂停。
- 账号的inauthentic(bot)/spam举报要在裁决时满足至少1帖被官方永久隐藏且官方动作至少100（帖/回复/转发/赞）；条件不齐则驳回，无分也无暂停，不追溯补分，可以后再报。有效封号每个举报队15分。
- 账号其他举报理由由人工处理，不赚Blue。平台LS.6.5的恶意举报风险仍要显示。
- 我们自己的审核结果不是平台版主结论，不能触发上述计分、隐藏、封号或暂停标记。

## 6. 推荐审核流程

### 6.1 输入和责任

使用独立审核任务、提示模板和服务配置，角色写作模型不能自批。审核模型可与写作服务相同，但必须是独立调用；使用同一模型并不意味着真正独立或不会重复犯错。

审核输入包括：最终实际正文、动作、账号和绑定版本、目标帖子/作者/正文版本、回复父帖与必要根帖、转发原文、来源与可用性、必要近期行为，以及适用的正式规则版本、平台策略和服务用途许可。未知身份/同意/官方状态明确填unknown。

在普通持久化之前先做输入最小化、秘密和隐私检查；不得把命中的完整密钥再发给云端“帮忙审核”，也不能先写进普通drafts后才检查。命中仅保存类型、位置、安全摘要和必要的受控隔离引用。不要将团队码、Cookie、Authorization、真实成员邮箱/姓名、私信或整库资料作为默认审核上下文。扫描范围须覆盖实际发送给审核服务的完整序列化messages，包括来源、记忆、规则引用、URL查询及诊断片段；最终社交写入前再次扫描实际body。脱敏的上下文不能成为批准含秘密原始正文的依据。凭据检测无法保证捕获所有格式，需限制输入来源。

帖子、引用、新闻、角色记忆及抓取网页一律作为待检查的数据，不能改写审核规则或授权执行。审核模型不具备凭据读取、网络命令或发布工具；即使其输出含工具调用或越权指令，服务端也拒绝。链接若需要验证，应采用安全的受控读取，禁止执行页面指令、任意内网请求、脚本或下载运行；读取前检查URL本身有无秘密，每次重定向重新检查地址及许可，记录最终地址、内容指纹和观测时间。媒体范围包括转发原文及必要父帖中的媒体和外链；尚无对应媒体能力时应记录能力缺口，不能仅凭模型看URL自动判安全。

本节首先保护新增审核出口。如果要声称“全部模型调用都防泄漏”，还须将同一完整出站检查接入已有写作、资料筛选、研究等调用；发布后才审核无法补救已传给写作服务的秘密。实际HTTP认证字段仍通过已选服务的预期认证通道处理，不进入提示、日志或普通记录。

第一阶段覆盖：

| 对象/动作 | 覆盖 |
| --- | --- |
| post/reply/带评语repost | 最终正文＋上下文；转发还需检查原文 |
| 空白repost | 检查被传播内容，不能因正文为空跳过 |
| like/follow | 对象及近期行为风险；不把他人原帖每个问题自动归罪于单次点赞/关注 |
| unlike/unfollow/本人删帖 | 校验身份、目标、授权与既有删除确认；它们是撤回/清理动作，不因被撤内容本身违规或审核服务故障而禁止清理，不强制无意义的内容模型调用；保留原发布审核与清理审计 |
| 注册/公开资料 | 名称/身份/公开介绍单独接入；正文审核覆盖不到注册入口 |
| 读取/skip/核对 | 不新添内容审核模型调用；沿用访问控制/隐私/限流。审核暂停时不能把关联通知自动标为处理完成 |
| 导出/公开代码/现实宣传 | 列入独立出口检查；本轮设计不增加这些外部执行能力 |

### 6.2 顺序

内存中取得候选 → 最小化与本地秘密检查 → 安全持久化候选 → 权限/目标/接口检查 → 按适用性完整选择条款 → 完整审核请求再扫描 → AI语义审核 → 本地校验AI输出及证据 → 持久记录 → 执行器校验批准指纹 → 共享额度等待 → 真正发送前再检查批准与实际body → 单次远端写入 → 原有结果核对。

已有历史草稿也要在进入新审核流程时先扫秘密；命中后普通列表/导出不再回显完整秘密，必要隔离处理需保留可追踪的安全记录，不能静默销毁官方审计或研究数据。

条款选择以动作/场景的确定性适用矩阵为基础；核心禁令全覆盖。不能只靠向量检索top-K选条款，否则可能漏掉不相似但适用的禁令。预算不足应拒绝该次自动审核并保留草稿，不能静默丢弃规则或关键原文。

AI只返回：匹配的既有rule_id、原文命中片段和字符位置、条件满足/不满足/未知、适用范围、支持/反对证据、尚缺资料、简短理由。每一适用类别要有检查状态；不得只返回一句“安全”。

服务器检查：ID在当前批准规则集内、层级未被AI改写、片段确实存在于本次输入、证据未越权、输出结构完整、所有必检项有状态。引用存在只证明没有编造引用，不保证语义判断正确，仍需验证样例和人工复核。

### 6.3 状态与放行

审核状态与执行状态独立。审核任务有pending/running，结论分：

| 结论 | 自动执行 |
| --- | --- |
| pass | 主赛/适用服务要求检查通过，必要信息充分；其他门也通过才可发送 |
| pass_with_platform_warning | 仅有平台策略风险；按明确配置的本地策略处理，不能伪装为主赛违规或默认接受全部风险 |
| blocked | 有依据的明确禁令或确定性执行门不满足；修改/补足后重审 |
| needs_human | 目标身份、语境、许可、伦理边界或规则冲突未解；暂停该动作 |
| error | 模型失败、429、截断、无效JSON、证据无效、规则集不完整；保留草稿，不能失败自动放行 |
| stale | 正文/账号/目标/上下文/规则/配置已改变，已有批准失效；需重审 |

不适用语义审核的清理动作可由确定性检查产生pass，记录review_kind=deterministic及不适用条款；不能用同一路径放行本来需要语义审核的发帖/转发。主赛硬约束不能通过普通“确认执行”绕过。人工可以指出AI误判、补证据、触发重审；需要解释的规范性例外应记录官方解释及适用范围。不能把模型自己改口当作官方许可。

建议首版默认只自动放行pass；轻微平台风险可做显式策略选择，高风险伦理/现实伤害疑点保持待人工。允许项如正常多账号/虚构人设应在适用性层正确处理，不能因此让整个系统长期卡在“bot违反LS”状态。

审核不自动重写草稿。若提供改稿功能，它产生新版本并完整重审；不能循环换模型重试直到得到放行。审核超时可有受控、持久化退避，取消/配置变化使迟到结果失效。

### 6.4 指纹、并发与恢复

批准绑定：精确最终正文（保留标点/大小写/不可见字符语义）、动作、账号绑定、目标ID与内容版本、上下文快照、规则内容哈希、策略版本、审核服务/提示/校验版本；审核服务记录实际模型、协议、目的地址及配置revision，不能仅绑定可复用的provider ID，也不保存密钥。不能复用现有为去重而做NFKC/大小写折叠的body hash作为唯一合规指纹。

不能只绑定draft.version，因为进入sending时正常递增也会误失效。应有独立review_input_hash。审核开始与写回用比较并交换，除输入哈希外必须核验job_id、attempt/lease token、owner/revision及未取消状态；否则同一输入在租约失效后重审，旧任务仍可能迟到覆盖新结果。输入变更丢弃旧结果；同指纹去重，进程重启只恢复有效任务，过期租约可安全重领，不能重复外部动作。

批准指纹与实时执行授权分开：enabled、角色模式/动作权限、取消状态、账号绑定、租约和额度由发送门实时校验；不要把整份动态settings/rate JSON放进内容指纹，以免正常额度刷新导致无限重审。若存在多进程，配置revision与发布授权还需数据库中的一致协议；现有进程内dispatch lock不能同步其他进程设置变更。

模型调用必须在数据库事务、发送锁之外。原子reserve及等待额度后的最终发送门仅快速检查已保存的批准。最终门应包含当前目标版本和所有相关设置，不能把execute早先获取的缓存对象称为“当前版本”。在门前通过受控读取取得必要的新观测/版本证据，超龄或无可用版本时刷新或暂停；目标有可见变更、必要上下文过期时重新审核。远端若不支持按版本条件写入，重新观测到实际发送之间仍有竞态，不能保证绝对同步或将其描述为已彻底解决。

动态行为风险需纳入近期状态或另设有效期；等待期间新增行为/额度/官方状态变化，需重算相关检查。规则变更应使相关待发送批准失效；unknown/uncertain远端动作仍走原有核对，不能因为规则变化自动再发。

审核门在reserve前拒绝：保留安全候选、不消费发文额度。在sending后但SDK尚未调用时拒绝：记录“已证明未发送”，按现有DeliveryNotStarted/restore_reservation及额度退款语义，释放本动作的去重占位、reservation、publisher lease和已预留配额，审核标stale/blocked，保留可修改草稿；不能走通用网络错误变成uncertain，也不能直接当完成skipped被清理。已经实际发出且无法确认的请求则必须保持uncertain，不得退款重发冒险。

## 8. 验收样例

以下是未来实现后的行为验收要求，本轮未运行模型效果测试：

1. 正常支持/反对虚构疫苗政策、虚构人设、多角色账号、附条件赛内假消息不被一律判禁。
2. 受保护特征逐类覆盖，含引用/批判仇恨的反例；人身攻击与政策批评分开。
3. NPC系统操纵命中；正常人物说服不误报；对手Agent许可、身份未知、混合受众、取凭据行为分别处理。
4. 色情媒体/链接、纯文本平台条款区别；不可访问媒体保留能力缺口。
5. 本地先拦真实秘密，审核服务、日志、异常、备份和导出均不含秘密。
6. 空白转发检查原文；点赞/关注看行为背景；清理违规帖的取消/删除不被内容门反向阻止。
7. 4/3提及数、500字符、共享团队额度、官方模型共享并发、Retry-After不被绕过。
8. 人工修改正文、换目标/账号、配置/规则升级、目标编辑、等待配额期间变化均使旧批准失效。
9. 新旧自动草稿、手动新建/直接API发布、并发重复审核、取消后迟到响应、重启与租约恢复均覆盖。
10. 模型无效ID/伪造片段/缺必检类别/截断/超时/429均不自动放行；同一问题不能通过反复重试“洗成通过”。
11. 审核被拦/待人工时不误确认通知、不重复执行；既有uncertain核对和单次发送语义继续成立。
12. 所有规则ID都可追到来源；每项禁令至少有命中样例和适用边界反例；平台风险和官方硬禁令不会互换标签。
13. 正文安全但上下文含密、普通持久化前拦截、同哈希旧租约迟到、最终门预留后证明未发送、缓存目标未刷新、多进程配置变化及审核服务不可用时的合法清理，均有独立验收样例。

真实模型需要用这些带人工依据的样本评测漏判、误判、待人工比例，并按规则类别查看。协议测试通过不能宣称审核“无遗漏/100%正确”。

## 9. 实施顺序建议

先完成规则库、来源冲突和用途许可核实；再做本地门与独立审核任务；随后接统一发送门和页面；最后用固定样例评测并接真实运行。只做“生成提示词加几条禁令”无法满足需求。

新规则获取可在系统中设计为启动前/版本过期时检查，采用官方页面指纹、章节数量与抓取状态判断；本轮不创建定时任务。新正文先生成待核对版本，不能让网页文字直接变成执行指令。404/登录墙/正文异常应标核验失败，不能把空页面当“删掉所有限制”。重大禁止项更新需暂停相关未发送动作；审核模型不得自行改规则。

## 11. 页面位置、开关与英文要求（用户本轮补充）

本节为最新产品设计要求，覆盖前文“首版无需独立入口”的建议；仍仅为设计，没有接入真实服务或修改运行设置。

### 11.1 导航与页面

在截图的同一排加入第4个步骤“AI 审核”，排列为：内容分析 → 资料筛选 → Agent 管理 → AI 审核 → AI 设置。前四项显示01–04，AI设置保留齿轮；建议路由 /ai/review。当前浅色背景、绿色选中态、圆角卡片和间距沿用现有风格，窄屏换行。

页面按以下顺序展示：

1. 当前生效状态与“比赛条款 AI 审核”开关。
2. 审核/语言判定连接及平台风险处理策略；从已有文字AI连接中选择，不另填密钥。
3. 常驻语言要求卡：English only，允许emoji与表情包，明确标“本队要求”。
4. 审核记录与规则依据两个标签页；点击记录展开正文证据、条款来源、语言结果、缺失项及后续操作。

首版无需通过率、风险概率等统计卡。草稿旁同时显示语言结果、条款结论与实际执行状态，例如“英文符合 · 条款通过 · 待人工确认”；审核通过不改变角色原来的人工审阅/自动执行模式。

### 11.2 开关的具体含义

开关名为“比赛条款 AI 审核”，只控制额外的条款语义复核。英文发布要求、权限、秘密检查、限流和本队原有策略始终检查。关闭不代表比赛禁令不再适用，也不代表关闭所有模型调用：必要的独立语言判断仍可能使用所选文字连接，页面必须写明。

开关、模型连接和平台风险策略统一编辑，点击“保存审核设置”后才生效；有未保存修改时显示标记，当前生效状态不跟着表单假变。实际保存以服务端成功回执为准，版本冲突保留成员输入并提示载入最新配置。保存配置本身不请求模型、不发布内容。

首次接入不静默打开比赛条款审核；正常开启前需选可用文字连接。已开启但连接失效时显示“已开启 · 暂停”，只暂停需要审核的相关外发，保留阅读/生成/历史查看与安全清理功能。不能静默换用其他模型或失败自动放行。

开启后所有尚未发送的待办在执行前补审；已经发出或uncertain的动作继续原有核对。关闭后取消相关未完成条款任务，使其迟到响应失效；原blocked/needs_human/error等审核挂起动作仍保留、逐条重新提交，不瞬间批量重放。历史结论保留当时模型、规则版本和时间，旧内容不倒填“当时已审核”。

平台风险策略可选“保留草稿，转人工复核（推荐）”或“仅提醒，允许继续”，只影响已明确属于平台层的风险；开启条款审核时，不能通过它覆盖主赛硬禁令。

### 11.3 仅英文，表情允许

这是用户明确要求的本队语言限制，拟登记为U01/english_only，并非官方条款新增禁令。正式实现后不提供普通关闭入口，避免关闭条款审核时顺带放行中文。

检查本队发帖、回复、引用/转发附言及被转载原文中实际向外传播的自然语言。阅读资料、目标父帖背景、中文人设编辑、后台理由和本工作台界面可以使用中文；不会因为角色读到一篇中文资料就判发布不合格。角色原有对外语言配置统一受English only约束，不能继续另选中文发言。

| 示例/情形 | 设计结论 |
| --- | --- |
| 完整英文句子，包含🙂、❤️、👏等emoji | 符合 |
| 单独的emoji/表情，含肤色、ZWJ组合、旗帜等 | 语言符合；仍检查该动作自身是否允许该内容/空正文 |
| 数字、金额、标点，配合英文或独立非语言表达 | 不作为其他语言拒绝 |
| 英文夹中文、整段法语/西语等，即使全部使用拉丁字母 | 不符合，保留原稿并标出非英文片段 |
| 英文中的正常专名、缩写和借词，如Kingstonia、IHO、café | 不因非ASCII、大小写或词典未收录自动拒绝；仍结合整段语境判断 |
| URL、已验证账号提及等技术标识 | 分字段识别，不单凭域名/账号拼写判正文语言；不能把整段外语伪装成标识豁免 |
| 语义性的中文话题标签、引用的中文句子、转载的非英文正文 | 属于公开传播文字，应修改/换目标后再检查 |
| 表情包/贴纸/动图 | 表情内容本身允许；本设计暂按“其可读配字也须英文”处理。不能假定图片没有文字或宣称当前文本SDK已支持上传/OCR；无法读取必要文字时待确认，具体带字表情包例外可随用户后续要求调整 |
| 短语歧义、混合语言证据不足、所需语言判定失败 | 待确认/检查失败，不冒充已符合，也不自动认定违规 |

英文判定不能仅用ASCII范围或“没有汉字”判断。先做Unicode脚本、emoji序列、技术字段和确定性片段识别，再对需要语义识别的文本调用已选文字模型。条款审核开启时可以在同一次独立审核中返回语言结果，避免对同一正文重复调用；关闭时必要的语言判断独立运行，共享同一预算。无连接或失败时，只有能确定符合的表情/非语言等内容可走确定性通过，其余相关外发保留待确认。

语言输出至少包含符合/不符合/待确认、命中片段与字符位置、判定对象（自写正文/转载/图片文字）和本队策略版本。界面用“语言不符”，不能显示“违反官方规则”。语言符合不等于内容合规，emoji/表情包也仍受内容规则检查。

不静默翻译或自动重发。可提供“改为英文”的草稿建议，先展示新旧内容，保存新版本后重新检查；被拦片段旁提示“请改为英文，表情可以保留”。

### 11.4 页面交互验收

校验未保存开关与实际状态分离、模型未选不能正常开启、连接失败显示暂停、关闭不重放旧动作、条款关闭仍显示英文要求、语言结论和官方结论分别展示、所有展开记录能显示依据。英文样例需覆盖emoji组合、纯表情、英文加非英文、纯拉丁字母外语、短缩写/专名、URL/提及/标签和带字表情包；这些是未来功能验收要求，本轮没有宣称真实模型语言识别已通过。

## 12. 用户后续修订（2026-10-21，覆盖第11节开关语义）

关闭审核时跳过全部 AI 审核：不调用审核模型、不要求可用连接、不要求审核批准、不新增审核记录，也不因无法本地确定语言或媒体文字待识别而额外挂起。仅保留无 AI 的本地英文基础检查，明确中文等非英文文字会提示修改；未知拉丁词不视作已确认英文，但关闭时不请求模型或阻塞原流程。

表情、颜文字、特殊符号正常允许，包含组合emoji、旗帜、肤色、颜文字中的假名/希腊字母以及箭头、数学符号。识别颜文字时采用有限字符及边界规则，不把括号里的普通中文句子作为表情豁免。

关闭后解除本模块导致的挂起和审核额度等待；原有生成取消后的人工确认、角色人工审阅模式、互动限制、身份检查、平台限流和已发出但结果不确定的动作保护保留。已经发出的动作不重新发送。开启后仍执行完整的独立 AI 条款与语言复核。
