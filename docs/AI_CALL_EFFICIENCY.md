## 0. 结论（花费视角，背景）

1. **钱快用完了。** 两个 OpenRouter key 累计花了 **$11.56**。今天（UTC 前 15.2 小时）花了 $7.85，折合 **约 $0.52/小时、$12.4/天**。`/api/v1/credits` 实测：总额度 $20，余额 $8.31（15:21 UTC），**照这个速度约 16 小时后用完**。而且余额越低，在途额度越小，402 会更早变多。
2. **输入占花费的 2/3，输出占 1/3。** 每天约 3,850 万输入 token、520 万输出 token，输出里 83% 是思考。按调用类型分：
   - Agent 决策约占 56%；
   - **选读（阅读选择）约占 34%**：每天 1,187 次调用，系统里**没有任何 token 记录**；
   - 失败作废的约占 9%；
   - 内容研究、事实提取、审核加起来不到 2%。
3. **实际单价是最便宜可用服务商的 2–8 倍。** 按 token 量和账单反推，平均每百万输入约 $0.21、输出约 $0.84，和 DeepSeek 官方价（高峰时段翻倍）差不多。而同一模型支持结构化输出的服务商里，最低只要输入 $0.02–0.10、输出 $0.15–0.50。我们没有记录每次调用实际由哪家服务商处理，所以还查不清原因。
4. **缓存基本不可能命中。** OpenRouter 默认用"第一条 system + 第一条非 system 消息"做黏性路由。我们第一条 user 消息每次都是整包动态 JSON，所以请求会被分散到约 20 家服务商，各家缓存都是冷的。同时也没有记录 `cached_tokens`。另外，每次调用里固定不变的部分（规则、人设、护栏）约 2–3.5k token，每天大约要按全价重复发送 500 万 token。
5. **"各自为政"体现在 6 个地方：**
   - 并发控制有两套，互相不知道对方；
   - 402 被当成普通 502：不等待，也没有冷却；
   - 三处 `max_output_tokens` 设置被代码悄悄丢弃；
   - 思考模式只能整条连接统一设置，`disabled` 会被强制改回 `auto`；
   - 研究和雷达的调用绕过了 Agent 的预算层；
   - 失败的调用不记 token。
6. **分段流程目前很贵。** 上线 2 小时里，"两次没通过检查"有 46 次，同期成功的回复只有 38 条，写作失败率约 55%。算上选读和失败，平均**每发布 1 条回复约用 10 万输入 + 2 万输出 token，约 $0.04**；单次流程每条草稿约 $0.011。重载后只剩发帖和回复两种动作，每轮都要写作，这项浪费会放大。
   - 根因 A 已经查清：检查步骤看不到人设里的事实和背景，所以判成 Unsupported。由 A 修，本方案不重复（见 E6）。

**最省钱的几项**（按每天节省的金额估算，都基于现在的调用量）：

| 项目 | 每天节省 |
|---|---|
| E8 服务商价格上限（D14 已取消） | $3.5–7（要先拿到 E1 的数据确认） |
| E7 选读瘦身 | $2–4 |
| E6 校验前移（和 B、A 一起做） | $1.5–4 |
| E4 分步调低思考 | $2–2.5 |
| E5 稳定前缀 + session_id | $1–1.3 |

E1（逐次记账）、E2（402 处理和统一闸门）、E3（max_tokens）本身不直接省钱，但它们决定了能不能测量、会不会出现 402 连锁失败，所以要最先做。

- 资料本身重复不多：同一 Agent 相邻两次选读，选中资料的重合度（Jaccard）中位数只有 0.09；相邻两次决策的资料重合度中位数是 0。选读缓存的命中率是 9%。

## 4. "各自为政"具体在哪

| # | 现象 | 证据 | 后果 |
|---|---|---|---|
| F1 | **两套并发控制互不相知** | Agent 调用走 `agent_budget.model_call`：第三方连接的租约 key 带每次请求独立的 uuid，等于不限并发。研究、雷达和交互调用走 `ai_routes.invoke`，只受 `BoundedSemaphore(2)` 限制，不经过 `model_call` | 没有全局上限，也没有按优先级排队。雷达和 4 个 Agent 可能同时占用在途额度 |
| F2 | **402 被当成普通错误** | `_request_json` 只识别 429；402 落到通用的"AI 服务请求失败"（502），不读 Retry-After，`model_call` 也不冷却 | 34 次/天失败，前面已完成的选读和决策白做。官方文档说 `openrouter_in_flight_budget` 的 402 是暂时性的，应该按 Retry-After 等待 |
| F3 | **输出上限被悄悄丢弃** | `ai_providers.complete` 不发送 `max_tokens`；`ProviderStore._read` 把 `max_output_tokens` 强制置空；`agent_competition.enhanced_max_output_tokens=1800` 和研究自动化的 `max_output_tokens` 也都不生效 | 没有 `max_tokens` 时，OpenRouter 按一个固定上限预扣在途额度，单次请求占用大；输出最长到过 26.6k，失控的长思考也停不下来 |
| F4 | **思考强度不能按任务设** | `thinking_mode` 只能整条连接统一设置，`disabled` 在存储和调用两处都会被改回 `auto`；`reasoning.effort` 从来没有发送过 | 选读（12 选 1 的排序任务）、检查（打分任务）也和决策一样深度思考：选读每次约 1.46k 思考，分段流程 90% 的输出是思考 |
| F5 | **提示词开头每次都变，也没带 session_id** | 决策、选读、写作的第一条 user 消息都是整包动态 JSON；人设、允许动作这些固定内容反而放在 JSON 末尾（`decide_messages` 是有意这样排的）。写作的 system 里还嵌了 `concern_hint` | 默认黏性路由的哈希每次都不同，请求分散到 -1017 的 25 个、v4.1-flash 的 30 多个服务商，缓存一直是冷的 |
| F6 | **记账不全** | `_safe_usage` 丢掉了 `prompt_tokens_details.cached_tokens`、`cache_write_tokens`、`cost`；成功调用不记录实际是哪家服务商处理的；选读、提取、审核和所有失败调用都不记 token；分段流程只记几步的合计 | 说不清钱花在哪，也无法验证缓存命中、服务商价格和每一步的成本 |
| F7 | **生成完了才校验，失败整轮作废** | 目标校验在 `_staged_decision` 全部完成之后；检查两次不通过就丢弃决策和写作；单次流程目标不对就整轮作废 | 见 3.2 |
| F8 | **选读本身很重** | 每次 48 条 × 320 字的目录加记忆，约 1.1 万 token，只为挑出 12 条；决策步骤还会再读这 12 条的全文 | 占花费 34%，却没有记录 |

## 5. 方案

每项写明：节省多少、改哪些文件、风险、怎么验证。节省额都按现在的调用量和反推单价（每百万输入 $0.21、输出 $0.84）估算。

### E1 逐次记账（P0-3 扩展）——最先做

- **做什么**
  - `_safe_usage` 保留以下字段：`prompt_tokens_details.cached_tokens`、`cache_write_tokens`、`cost`、`completion_tokens_details.reasoning_tokens`。
  - 结果里带上实际处理的服务商（SSE 元数据里已经有 `provider`，目前只在出错时保留）。
  - `model_call` 和 `ai_routes.invoke` 每次调用都记一行：调用类型（reading / decide / write / check / single / radar / research / extract / review / persona / interactive）、agent、连接、模型、实际服务商、HTTP 状态和错误码、`finish_reason`、各类 token、`cost`、耗时、首 token 时间、`max_tokens`、`reasoning`、session_id 的哈希。**失败的调用也要记。**
  - 新增只读脚本 `scripts/measure_llm.py`，按类型、Agent、服务商和小时汇总。
- **节省**：本身不省钱，但后面每一项都要靠它来验证。
- **文件**：`ai_providers.py`（共享文件，先公告）、`agent_budget.py`；`ai_routes.invoke` 需要改 1 处（A 的文件，用 Edit）。
- **存储（需要决定）**
  - 推荐：新建 `llm_calls` 表。需要改 `db.py` / `postgres.py`，这两个是共享文件，按顺序要排在 C 的 P1-1 之后，或请 C 一起加。
  - 备选：先不改表结构，在 `checkpoints` 里存按"小时 × 类型"的汇总，外加最近 300 次调用的明细。
- **风险**：低。每天约 3,000 次写入，记账失败不能影响调用结果（沿用现有"记账失败不改变结果"的写法）。
- **验证**：
  - 单测：SSE 最后一帧带 usage、cost、cached_tokens 时能正确解析；字段缺失时不报错。
  - 重载后：≥95% 的调用带 `cost`；按 UTC 日汇总的 `cost` 和 `/api/v1/key` 的 `usage_daily` 相差 ≤5%。

### E2 统一闸门 + 402 / 429 正确处理

- **做什么**
  - 在 `ai_providers.complete` 入口加一个进程内的优先级信号量。后端是单进程，事实提取、研究、Agent 都是这个进程里的线程，所以一处就能覆盖所有调用。
  - 默认并发 4。优先级：写作 / 检查 > 决策 > 交互 > 选读 > 雷达 / 研究 > 事实提取。
  - 402 的处理：
    - 带 `Retry-After`（`openrouter_in_flight_budget`）：在原地可取消地等待，然后重发**同一个请求**。402 是在生成开始前就被拒绝的，重发是安全的。最多等 60 秒、重试 2 次；期间把并发上限减半，等过了 Retry-After 再逐步恢复。
    - 不带 `Retry-After`（`weight_exceeds_budget` 或余额不足）：不重试，给出专门的错误码 `budget_exhausted`，并让低优先级的调用暂停。
  - 429 用同一套逻辑，取代现在只在 Agent 路径上生效的冷却。
  - 402 要映射成"等待"，不能当成错误。`agent_waiting.classify` 需要识别这个新的错误码（B 的文件，改 1 行）。
- **节省**：34 次/天的失败约浪费 50–80 万输入（约 $0.1–0.2/天），另外每次失败还白耗约 80 秒生成时间。更重要的是，余额变低时，在途额度会跟着缩小，这时不会再出现成片的连锁失败。
- **文件**：`ai_providers.py`、`agent_budget.py`、`ai_routes.py`（invoke 1 处，A）、`agent_waiting.py`（1 行，B）。
- **风险**：
  - 等待期间 Agent 租约会持有更久。现有的心跳续约可以覆盖；等待总时长设上限 60 秒，超过就转为 Deferred。
  - 信号量要保证在任何路径上都会释放（用 `finally`，加测试）。
- **验证**：
  - 单测：模拟 402 + Retry-After，确认重发的请求体和原请求完全一样；402 不带 Retry-After 时不重试；取消能打断等待；并发不超过上限；高优先级先拿到名额。
  - 重载后："AI 服务请求失败"降到 0；出现 402 时只有等待事件，没有失败事件。

### E3 按调用类型设 max_tokens（D4）

- **上限**：按 p99 留余量，并且要考虑到 E4 之后思考会变少。

| 类型 | max_tokens | 依据 |
|---|---|---|
| 决策（分段） | 12,000 | 只做决策一步时 p99 4.3k，最大 4.6k |
| 单次流程 | 16,000 | p99 9.6k，最大 18.2k |
| 写作 | 6,000 | |
| 检查 | 4,000 | |
| 选读 | 6,000（思考调低后 3,000） | |
| 雷达 / 研究 | 24,000 | 最大 13k |
| 事实提取 | 8,000 | |
| 交互 | 16,000 | |

- **做什么**：真正把 `token_parameter` 发出去（目前写的是"不发送"）。上限由调用类型决定，不再由连接决定。截断时沿用现有的"只重试一次"逻辑。
- **节省**：直接省下的 token 很少，只是砍掉偶发的失控长输出。主要作用是把每次请求的在途预扣从"固定上限"降到几分钱，**减少 402**。
- **文件**：`ai_providers.complete`，以及 `model_call` 新增 `purpose=` 参数。调用方各加 1 个参数：`agent_control` 和 `agent_reading` 是 B 的文件，`fact_extraction` 和 `ai_routes` 是 A 的文件，都用 Edit，并在协调板公告。
- **风险**：被截断后要重试一次，反而多花钱。所以要监控 `finish_reason=length` 的比例，超过 1% 就调高对应类型的上限。另外要注意：上限包括思考 token。
- **验证**：单测检查每种类型的请求体都带了对应的上限；重载后 24 小时内截断率 <1%，402 次数明显下降。

### E4 分步调低思考（P2 补充一）

- **做什么**：在调用层加 `reasoning` 参数，按调用类型设置；连接本身的 `thinking_mode` 不动。

| 调用类型 | 设置 |
|---|---|
| 决策 | 保持 auto |
| 写作 | `effort: low` |
| 检查 | `effort: low`（试验后再看能不能改成 `none`） |
| 选读 | `effort: low` 或 `none` |
| 事实提取 | `effort: low` |

  两个 DeepSeek 端点都支持 `reasoning` 和 `reasoning_effort`。
- **节省**：
  - 选读：每次约 1.46k 思考降到约 0.3k，每天少约 140 万输出，约 **$1.2/天**，每轮生成快约 10–20 秒。
  - 写作和检查：每次约 1.2k 思考可以省掉。重载后估计每天 500 轮写作，每轮约 2.5 次调用，合计约 150 万输出，约 **$1.3/天**，每轮快约 30–50 秒。如果检查失败率还停在 55%，省得更多。
- **文件**：`ai_providers.complete`（接受按调用设置的 `reasoning`）、`agent_budget.model_call`（按调用类型给出策略）。
- **风险**：
  - 写作不思考，可能编出更多资料里没有的说法；检查不思考，判断可能变差。
  - 这和用户之前的设计（思考模式 auto）不一致，需要协调会话拍板。
- **验证**：
  - 用 ≤3 次真实调用确认参数被服务商接受、`reasoning_tokens` 确实下降，并记下花费。
  - 再挑 1–2 个 Agent 试跑 2 小时，对比检查通过率、Unsupported 比例、方向判定的分布和每轮的花费。

### E5 稳定前缀 + session_id（P0-4）

- **做什么**
  - 每次请求带 `session_id`：Agent 用 `ctn-<agent_id>`（同一 Agent 的各步走同一家服务商，各模型分开黏住）；后台任务用 `ctn-radar`、`ctn-research`、`ctn-extract`。
  - 消息改成三段：[固定 system] → [第一条 user：固定块，即人设、允许动作、护栏、雷达优先级] → [第二条 user：本轮动态资料，任务要求仍然放在最后]。这样即使不传 session_id，默认的黏性哈希也稳定。
  - 写作模板里的 `concern_hint` 和 `question` 从 system 移到 payload。
- **节省**：
  - 能命中缓存的比例：决策约 3k / 16.6k，选读约 1.6k / 11.3k（如果记忆按稳定顺序排，还能更多），写作约 0.8k / 1.8k，检查约 0.5k / 1k。合计每天约 500–700 万输入。
  - 缓存读取按 0.1 倍计价；DeepSeek 首方端点甚至只有 0.02 倍。合计约 **$1.0–1.3/天**，首 token 也会更快。
- **文件**：
  - 调用层：`ai_providers.py`（`session_id` 字段）、`agent_budget.py`。这部分是纯增量，第一批就做。
  - 消息顺序：`agent_pipeline` 的 `decide_messages` / `write_messages` / `check_messages`。这个文件的修改顺序已经定好：B（P0-2）→ A（检查步骤和写作规则）→ D。**等 A 交出文件后再做**，到时在 A 的版本上用 Edit 改。
  - `agent_reading`、`agent_control` 单次流程（B 的文件）和 `concern_radar.messages`（A 的文件）：先和对方约定再改。
- **和 A 的改动有关**：A 会把全部生效事实（约 6.7k token）放到检查步骤 system 的开头，再加上人设摘要。
  - 这样每次检查的输入会从约 1k 涨到约 8k。按每天 500–1,500 次检查算，多出约 370–1,000 万输入，不走缓存约 $0.8–2.1/天。
  - 不过这一段对所有检查都一样，正好可以做成稳定前缀。带上 `session_id` 后能命中缓存，成本可以降到约十分之一。
  - 所以第一批要先上线 `session_id`，最好赶在 A 的检查改动之前，或至少同时上线。
- **风险**：
  - 消息顺序变了，模型注意力的分布也会变。原来把任务要求放在最后是为了防止长上下文"丢中间"，改动时要保留这一点。
  - 黏性路由会把同一 Agent 连续 10 分钟钉在同一家服务商；如果那家又慢又贵，就会一直慢、一直贵。要和 E8 的价格上限一起用。
- **验证**：先做 E1。重载后决策步骤的 `cached_tokens / prompt_tokens` ≥15%，写作和检查 ≥30%；决策结果的分布（动作、顾虑）和改之前没有明显差别。

### E6 便宜校验前移，失败时只重试出错的那一步（B 和 A 负责，D 只做计量）

- **由别的会话负责**
  - 目标校验放进决策步骤，不合格只重试决策：B 的 P0-2（D7 已批准）。
  - "两次没通过检查"：根因 A 已查清，是检查步骤看不到人设里的事实和背景。A 会让检查改用全部生效事实并放在 system 开头，再加入人设摘要，排在 B 的 P0-2 之后。本方案不重复。
  - `agent_pipeline.py` 的修改顺序是 B → A → D。D 涉及这个文件的部分（E5 的消息顺序）等 A 交出文件后再做。
- **D 的部分**：E1 分步记账，让失败调用、每一步的 token 和花费都看得见，用来验证上面两项的效果。
- **节省**（由 B、A 的修复带来）：
  - 现在：失败作废的决策部分加上失败作业的选读，约 530 万输入 + 77 万输出，约 **$1.5/天**。
  - 重载后：如果检查失败率还是 55%，会涨到约 $3–5/天。
- **验证**："两次没通过检查"和"目标不在资料中"都降到每 8 小时少于 5 次；每发布 1 条回复的花费从约 $0.04 降到 $0.015 以下。

### E7 选读瘦身（D12：解冻后第一项）

选读占花费的 34%，产出只是"从 48 条里挑 12 条"。三档，风险从低到高：

- (b) 目录从 48 条减到 32 条，每条片段从 320 字减到 200 字，选读输入减少 40–50%，约 **$1.1–1.4/天**。

- **验证**：对照组和试验组比较回复对象里"犹豫或偏 No 的 NPC"占比、决策失败率和每轮花费。

### 8.2 瓶颈在哪

1. **不是模型并发。** 平均只有 1.55 个作业在跑模型，接口还有很大余量。
2. **每个 Agent 严格串行。** 一轮是选读 → 决策 → 写作 → 检查 → 发布；发布完成或者等到额度之后，才开始下一轮。一轮的中位数是 127 秒，其中选读占 43 秒。草稿在等发布时（`waiting_publication`），连下一轮的选读也不允许开始。
3. **时间主要花在思考上。** 选读、写作、检查都在深度思考，输出里 83–92% 是思考 token。
4. **失败把吞吐砍了一半。** 分段流程上线后，每小时失败 26–32 次，有效发布从每小时 37–41 条降到 17–19 条。
5. **（更正）发现通知并不慢。**
   - 之前的"7.5 分钟"是测错了。收件箱里每条未处理通知的 `observed_at`，每次刷新都会被覆盖成最新的拉取时间（`agent_observation._finish_channel` 里的 `{**old, **item}`），所以它记的是"最后一次看到它还没处理"，不是"第一次看到"。
   - 实测轮询大约每 60 秒一次，所以发现延迟大约在 60 秒以内。真正慢的是处理：从对方发出到我们的回复发布，中位数 6 分钟，p90 41 分钟。
   - 另外，Agent 在生成期间会跳过轮询（tick 里排除了 running 状态），每个 tick 也只刷新一个 Agent。
6. **吞吐翻倍后，先撞上的是我们自己的额度。** 队伍自定义的发帖额度（1 条/分钟）现在用了 45%；平台允许 3 条/分钟，离那条线还远。

### 8.3 方案

### 8.5 实施记录

**第一批（2026-10-22，未部署）**：E1 记账、E3 max_tokens、E2 的 402 / 429 退避、`session_id`。

真实调用验证共 3 次，花费 $0.00036。用的是 openroute 连接，带结构化输出和 `require_parameters`：

验证中发现一个问题并已修复：流式用量会被清洗两次，第二次把已经展平的 `cached_tokens` 丢掉了。现在 `_safe_usage` 重复执行结果不变（幂等）。

测试：相关后端 4 组共 588 个全部通过（16 个仅 PG 的用例跳过），其中新增 `tests/test_llm_calls.py` 21 个。

- `llm_calls` 里出现 reading、decide、write、check 的记录，雷达跑过后还要有 radar；
- ≥95% 的调用带 `cost`；write 和 check 的 `cached_share` 大于 0；

第一批已在第二个重载窗口上线（git `084ffdf`）。重载后前 9 次调用全部带 `cost`，写作步骤的缓存命中率是 31%。

**第二批（2026-10-22，未部署）：S2 调低思考 + S4 统一闸门。**

S2 实测：用同一个写作请求、同一家服务商（Sail Research）各跑 1 次，共 3 次真实调用，花费 $0.0004。

| auto | 624 | 12.0 秒 | 433 字 |
| low | 266 | 6.9 秒 | 424 字 |

`low` 确实生效，所以按 D19 采用 `low`：选读、写作、检查、事实提取都设为 low，决策保持 auto。`none` 写作时会被截断，暂不用于写作。

S4：新文件 `llm_gateway.py`，所有记账的调用都先经过它。上限 6；后台任务只能用空闲名额，始终给 Agent 留 2 个。优先级依次是写作和检查、决策、选读、交互、后台；同一优先级里，在跑请求少的 Agent 先走。402 在途额度会让上限收紧到当前在跑的数量，直到 Retry-After 过去。排队时间计入 `wait_ms`。

**S9 只读定位**（24 小时，40 条回复通知的回复）：

|---|---|---|

- 同期一共发布了 156 条回复，只有 41 条是回复通知的。

  - 选读必须带上这些通知；
  - 决策提示里把"先回复回复我们的人"设为默认。
  - 发现延迟本身（轮询约 60 秒）不是瓶颈。
