## API、浏览器与去重

| 数据 | 实际行为 |
| --- | --- |
| 帖子身份 | 以官方 post_id 合并。两个 ID 即使正文一样也保留两篇；Latest/Trending 观测分开保存。 |
| 正文版本 | body、visibility、embed 内容指纹未变时不新增版本；记录最新见到时间。 |
| 互动 | API 与浏览器均保存 like_count、reply_count、repost_count、view_count、真实观测时间及来源。正文不变不会阻止互动快照。 |
| 重试 | 浏览器记录有稳定 UUID，入库回执避免重传再次插入。计数相同但观测时间不同仍保留；30 秒浏览器缓存命中不伪造新观测。 |
| 原始响应 | 相同来源、端点和载荷合并存储，快照仍独立引用，因此原始表时间不能当每一次采样时间。 |
| 两路协调 | 后端跳过 60 秒内已有浏览器样本的帖子；22:13 后核对未发现违反这一方向的重复请求。不是双向完全排他锁，近同时请求仍可能发生。 |
| 明细范围 | 当前主要是互动总数，不是完整点赞用户列表或每次点击事件；回复正文按公开 Feed 和有预算的回复分页采集。 |

## 尚需改善的边界

1. 快照唯一键目前是 (post_id, observed_at)。同帖、完全相同时间戳但载荷不同，第二条会被忽略；原始载荷仍在，但不进入分析快照。临时库已复现，正式库没有发现未被快照引用的计数载荷，暂未见实际碰撞。应改为明确观测标识及来源/载荷冲突记录，不能人为改采样时间。
2. 浏览器心跳“enabled”只证明已启用，不能等价于持续取得数据；应把最近成功响应/入库时间和等待共享冷却单独展示，并记录浏览器状态码，才能量化两条线路。
3. 现有多个非管理 Latest 标签页自身的请求不在协调器控制内；按要求保留、不关闭。团队其他程序也不受这台机器的协调器控制，所以仍可能 429。
4. 整体数据模型适合趋势分析，但采样频率不足以还原每帖全部变化。优先保证新帖基线和 30/60/180 分钟窗口；老帖采用分层复查，持续不可访问记录拉长重试，而不是简单增加请求或依赖 VPN。

官方 SDK 的 counters 说明为点赞、回复、转发、浏览总数，存在约秒级延迟；likers 是另一个接口：[官方代码](https://github.com/capturethenarrative/pypi-capturethenarrative/blob/main/src/capturethenarrative/legitsocial.py)。本报告的现场结论来自本地真实日志和数据库。
