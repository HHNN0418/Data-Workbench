# API / 浏览器采集平衡方案

核验：2026-10-19 22:27 Australia/Sydney。本文为基于现场数据的实施设计，尚未部署新调度器或 Docker；现有 API 保持直连，浏览器代理和现有标签页保持原状。

## 已确认的瓶颈

- 最近四轮耗时 103.5、136.8、140.6、130.3 秒，轮末再等待 60 秒。
- 每轮等待共享许可 / 限流约 84.6–119.9 秒。已有共用限速，但执行仍以整轮串行为主，部分互动窗口任务先于 Latest，造成新帖发现延迟。
- 目前约 8054 篇帖子。即使把本地互动预算 200 次/分钟全用于遍历，也要至少约 40 分钟；不能承诺全量分钟级互动历史。
- 浏览器已经能补充正文和四类互动，历史接口分页仍需要 API；两者使用同一平台数据，额外出口不等于额外公开信息。

## 调度与分工

1. 单一调度器维护持久任务队列。任务具有类型、对象、到期时间、优先级、租约、尝试次数和失败原因。以端点组控制总量，仍尊重 Retry-After，不按代理数量放大配额。
2. Latest 新帖发现独立调度，初始目标 30–60 秒检查一次；分页追赶和历史游标分开，优先补新旧水位之间的缺口。目标受实际配额和冷却限制，不是保证。
3. Trending 初始目标 2–3 分钟刷新排名；历史回填只使用剩余 Feed 名额。浏览器不再和 API 各自重复定时抓相同列表，由调度器决定哪个通道执行。
4. 互动预算按数据需要分配，不按 API/浏览器各一半。初始保留：新帖基线 40%、到期 30/60/180 分钟分析窗口 40%、历史公平轮巡 20%；空闲份额互借。窗口临近截止、积压持续增长时动态调整，并记录被推迟的任务。
5. 浏览器负责现有页面可观测帖子及本队总分/活动流水；公开帖子采样与 API 任务使用同一租约。后台优先填补浏览器未覆盖对象；不将浏览器只在热门页面看到的样本当成随机总体。
6. Feed 冷却期间，调度器继续执行未受限的其他任务；互动分小批执行，到期的新帖任务可插入，不等一整轮数百个任务结束。
7. 近期实际快照跨通道复用。浏览器要刷新而后端刚采过时，可返回带原始观测时间的缓存结果；缓存读取不生成新快照。租约过期允许恢复，入库仍需幂等，不能宣称网络请求绝对只执行一次。
8. 连续 404/410 对象延长退避，并区分当前不可访问与待采；保存旧数据和引用关系，不写伪造零值，也不把原帖计数移给转发对象。原帖仍可独立采集。

## 入库及验证

- 所有执行器通过本地 FastAPI 入库，单一写入入口维护 SQLite；不让多个容器各写一份数据库再拼接。
- 优先修复同帖同时间戳不同计数的冲突：保存明确的观测标识、来源及载荷指纹；相同观测重传幂等，冲突保留并标注，分析不重复累计。
- 新增浏览器逐请求状态码 / 耗时 / 等待原因的最小遥测，不保存认证头、Cookie 或私有页面内容；现在缺少这些指标，不能证明 VPN 相比直连降低了多少 429。
- 验收至少比较连续多轮的新帖发现延迟 P50/P95、首次互动延迟、30/60/180 分钟窗口完成率、未采积压年龄、重复请求率、各通道成功 / 429 比例以及来源覆盖偏差。不能只以 HTTP 200 数或快照条数判定优劣。
- 保持页面数量和 VPN 节点不变进行改造前后对照；所有原页面保留。

## Docker 与 NordVPN

技术上可把采集执行器放进 VPN 网络环境，而 API 执行器保持直连。NordVPN 官方有 Linux Docker 构建说明，容器 VPN 不自动代理宿主机：[官方说明](https://support.nordvpn.com/hc/en-us/articles/20465811527057-How-to-build-the-NordVPN-Docker-image)。当前 Chrome 扩展的安装/登录不等同于容器已获得登录状态，容器化还需独立处理运行环境、会话和故障恢复。

现在不建议部署多个代理采集器来扩大请求量。赛事主规则 §5.2.2 涉及禁止干扰限流，§6.3 要求遵守限流；不能把换出口直接解释为获得新的团队配额：[主赛规则](https://capturethenarrative.com/info/competitions/2026/rules/)。多执行器可用于任务隔离和故障恢复，但仍应共享预算；只有主办方明确给出允许的独立额度或批量数据入口，才据此扩容。

实施顺序：先补观测与冲突处理，再改统一任务队列和分工，然后用现场指标验证覆盖改善；最后按运行稳定性需要容器化。此顺序可以区分调度收益与代理收益。
