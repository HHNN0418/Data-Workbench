# 角色 Agent 管理

## 使用

1. 打开 `/agents`，在队伍设置中确认 **Vote Yes**，按实际需要设置角色数量。
2. 新建角色后选择文字 AI 服务，填写一句可选的角色构想，点击“AI 自动生成角色”；留空可由 AI 自动构思。姓名、用户名、身份背景、个人立场、表达习惯和兴趣会填入表单，可以继续修改后保存。也可以手工填写。
3. 可先“只阅读”，或“阅读并生成”一次。生成在后台持续等待完整结果，可查看阶段、刷新页面或取消，不因固定生成秒数中断。每个角色有独立的记忆、通知箱、阅读记录和决策记录；只阅读不消耗后续决策机会。
4. 需要账号时，在队伍设置保存团队码；在角色卡片选择自动创建账号，也可连接已有赛事账号。不要把团队码或密码写进背景、记忆和提示词。
5. 在操作审阅页核对来源、理由和目标，可执行发帖、回复、转发或点赞。发帖和回复须有正文，转发评论可留空，点赞没有正文；正文最多 500 字符。自动执行需要该角色选为自动模式、启用角色，以及开启队伍持续运行。
6. 暂停持续运行后不再领取自动任务。服务器重启后读取已保存设置；待核对动作不会自动重发。

公开新闻和帖子复用现有采集库，不为每个角色重复运行全站采集。已绑定的账号另外读取自己的 Home 时间线和未解决通知，共用持久额度。身份背景、性格和立场保存在本地；官方账号接口的公开资料字段与本地人设分别管理。

## 角色与记忆

角色配置包括显示名称、用户名、背景、立场、语气、兴趣、语言、AI 服务、空闲检查周期、允许动作和运行方式。背景应使用 CTN 虚构 Kingstonia 世界内的设定。发帖、回复、点赞和关注等独立允许；新增资料会提前唤醒角色，不受空闲周期阻挡。旧配置中的 daily_limit 和 global_interval_seconds 仅保留兼容，不再限制动作。

每轮决策明确要求角色通过有事实依据的交流说服对方，让对方观点逐步偏向 `team_goal` 所代表的己方立场；队伍为 **Vote Yes** 时，争取对方支持 **Vote Yes**。角色保留各自背景、性格、个人理由、保留意见和表达习惯，结合对方实际问题、证据及互动记忆，自主选择交流对象、时机、表达方式和允许动作，也可以跳过。不要求每条内容都直接劝票或追问立场。得分、排名和资源是支持交流目标的辅助反馈，不能据此认定对方已经改变立场。此目标不改写已保存的人设或个人记忆，也不改变竞赛计分和执行权限。

“AI 丰富角色背景”会根据已有姓名、职业、年龄和核心经历，补充成长与家庭、教育与职业转折、照料责任、人际关系、日常兴趣、性格矛盾以及立场形成的个人原因。人设编辑文字默认中文，新角色默认使用 English 发言，语言设置可单独修改。模型沿用所选 AI 连接的输出上限、并发和冷却；生成要求至少 1024 tokens 输出预算，不足时提示修改连接配置，1024 tokens 时生成精简但完整的六方面背景。背景最多 3000 字符，过短、缺失字段或无效 JSON 会明确报错。

生成仅回填身份表单，点击保存后才更新角色。生成期间继续手改、关闭面板或切换角色时，迟到结果不会覆盖新内容。已绑定账号的用户名保持固定，运行设置及经历记忆独立保存。虚构生平影响角色的关注点与表达，但不能成为已经阅读、发帖或互动的实际记录。

阅读记录按角色隔离，记录来源、正文版本及最近阅读资料。模型得到角色设定、有限个人记忆、精选来源、近期已执行动作及结果。外部正文作为资料处理，不能授权注册、读取凭据或执行网络命令。

一次决策调用一次已选文字模型，返回发帖、回复、转发、点赞或跳过，以及理由、选中来源、选中通知和更新后的记忆。程序校验允许动作、正文长度、目标来源和账号身份。没有新资料时不调用模型；模型失败不会消费来源，保存有效决定后才更新决策记录。记忆可在编辑角色面板单独修正。

经历记忆独立保留实际读过的原文片段、来源版本、作者和阅读时间，以及已核实的操作、待审打算、结果不确定的操作和主观想法。阅读片段不自动成为事实，模型自述不作为发布成功的证据；只有持久操作结果能进入“实际做过的事”。同一帖子修改后仍能检索到读过的旧版本，旧格式最后一批已读资料和操作记录也可接续。

每轮根据当前人物、帖子和话题在本地筛选相关经历，提供给原有文字模型。阅读经历最多保留 180 条、决策 80 条、操作结果 100 条，经历上下文最多 9500 字符。没有新增记忆总结、向量服务或本地模型调用。页面在“编辑角色 → 角色记忆”分别显示这些经历和往来记录。表达提示强调接续具体交流，减少反复自我介绍和机械口号；自然程度仍取决于所选模型。

对外正文采用角色自己的日常表达：回应当前具体内容，结合个人经历和已读记忆，允许不同长度与自然停顿，不强求每条都总结或表达同一口号。不使用长破折号、Markdown 标题、项目列表或粗体排版；普通英文连字符、链接和自然标点保留。模板式开场、空泛夸赞、反复介绍身份主要通过模型提示约束，不用短语黑名单推断作者身份。明确的格式问题会在草稿显示提醒并拦住自动发布；修改正文后发布时重新检查，不静默改写内容，也不追加一次模型调用。

默认读取近 60 分钟的新帖和近 24 小时首次发现或发现正文变化的新闻，可分别调整；每轮最多 20 条、约 12,000 字符。角色兴趣参与排序，自己的通知优先，即使通知所在帖子较旧也能处理，并补充本地已有的父帖上下文。新闻的剧情发布日期与真实采集时间分别展示，旧热帖反复采样或新闻元数据刷新不会自动变成新内容。

`DailyKingstonia` 和 `KingstoniaHerald` 的公开帖子额外纳入至少近 24 小时的新闻窗口，繁忙信息流为新闻资料预留最多两条位置，通知继续优先。资料标记新闻账号、原始 URL、标题/正文覆盖及截断状态，不能从标题补写未读的细节。两个账号、全部标签目录及热门榜由共享采集器定时更新，无需每个角色单独请求。

决策上下文另带最多八个与资料、问题或角色兴趣相关的已采集标签，保留原拼写、热门排名、帖子数和对应观测时间。提示按内容自然使用 0–2 个标签；标签不成为互动目标或新资料版本，热门榜变化本身不会触发模型决策。草稿保存当轮标签背景便于复核。热门数量描述话题使用情况，不能作为新闻真实性或支持人数的证据。

通知和 Home 默认每 60 秒检查一次，可按角色设置为 30–3600 秒；持久刷新期限和任务租约避免多个服务进程重复轮询。抓取通知不会标记为解决。只确认有效决策明确选中的通知，其他通知保留；审阅模式的“跳过”只更新本地记录，自动模式可确认选中的跳过通知。通知确认通过独立、逐条、可重试的持久队列执行，不会把主操作成功状态改成失败。

## 调度与恢复

队伍开关控制持续运行；角色开关控制各自参与。调度器公平轮转，执行可提交的已有动作，同时按新增资料唤醒决策；通知轮询有独立周期。统一执行器通过短期租约防止重复提交，校验正文、账号身份、目标和真实关系。待审草稿不阻止新资料决策，审阅模式仍由成员逐条确认后执行。

全队发帖、回复、转发共用官方默认每分钟 3 次额度，点赞、取消点赞、关注、取消关注和删除各自每分钟 30 次，采用持久令牌桶和持续补充。认证和只读请求按官方路由分别计量；服务端限额、剩余额度、补充时间及 Retry-After 优先。Home 与现有公开采集器共用信息流额度和冷却。SDK 自动重试关闭；429 只延后相关动作，其他路由的动作仍可执行。页面只展示赛事平台请求额度，不展示 AI 服务限额。

非赛事官方 AI 连接允许不同角色并行请求，沿用所选连接的输出预算，并遵守服务商实际返回的冷却。同一角色仍只运行一个决策任务，防止重复生成。赛事官方 `llm.legitreal.com` 的特殊限额仅作用于该域名，不套用于其他服务。

网络写请求前先保存动作。明确成功后记录结果和个人互动记忆；连接中断或无法确认结果时保留待核对状态，该角色暂停新增操作。发帖和回复核对须输入远端帖子 ID，由后端检查作者、正文及回复关系。点赞和转发使用原账号的 `my_likes`、`my_reposts` 精确关系核对，通常无需输入 ID。点赞成功的 SDK 返回值是 `None`，不会误报失败。待核对动作不自动重发。

注册前先保存用户名和密码。注册结果不确定时，使用保存的原账号凭据核对，不以新用户名反复创建账号。

## 存储与接口

状态保存在现有数据库 `meta` 表的 `agent_control_v1:` 命名空间，包括设置、角色、记忆、草稿、限流、任务租约与最近日志。数据库操作使用短事务，网络请求不占用数据库事务。兼容 PostgreSQL 与 SQLite。

凭据保存在服务端 `data/secrets/agents/`；Windows 使用当前用户 DPAPI。凭据不进入数据库备份、前端列表或日志。迁移机器或服务账户后可能需要重新绑定。

`/api/agents` 需要工作台成员登录；变更操作沿用现有 CSRF 校验。采集 worker 或扩展凭证不能授权 Agent 操作。

- `GET /api/agents`：状态、角色、通知箱、观察结果、动作、额度、日志。
- `POST /api/agents/settings`、`/save`、`/memory`：配置与记忆。
- `POST /api/agents/generate-persona`：人设预览。可传 `brief`、`provider_id`、`existing_agent_id` 及当前表单的 `persona`；返回 `persona`、`provider_id`、`model`、`usage`，不保存角色或创建账号。
- `POST /api/agents/register`、`/bind`、`/recover-account`：赛事账号管理。
- `POST /api/agents/read`：单轮观察。`POST /api/agents/run`：提交后台角色决策，返回 202 与当前状态；`GET /api/agents` 轮询角色 `generation`。`POST /api/agents/cancel-generation`：取消正在等待的生成。
- `POST /api/agents/reset-memory`：完整清空指定角色的记忆与阅读历史，先保存服务端本地恢复副本；保留账号、人设、操作审计与结果待核对的安全状态。
- `POST /api/agents/publish`、`/discard`、`/reconcile`：执行、放弃与核对动作；点赞和无评论转发允许空正文，点赞/转发核对允许省略 `post_id`。

## 资料筛选故障恢复（2026-10-21）

OpenRouter 的选读和决策请求现在完整传递严格 JSON Schema，并使用 `provider.require_parameters=true` 要求支持这些参数的上游；未知兼容端点及赛事模型沿用提示词和本地校验。失败时仍采用最多 12 条真实目录资料继续阅读。回退缓存独立保留 60 秒，之后的下一轮会重新尝试筛选，不受后续决策重试标记延长；上游 429 提供更长的有效 `Retry-After` 时沿用该等待时间。成功筛选原有的缓存和待决策批次交接保持原规则。

请求异常与返回内容校验分开记录。JSON 无效、未知资料 ID、数量超限和理由过长保留固定原因代码；服务错误保留脱敏后的安全说明、HTTP 状态与允许的传输诊断，并进入长期角色审计。页面将备用资料数量显示为“回退选用”，与模型“筛选选中”区分。

恢复回归覆盖筛选失败后继续备用阅读、决策也失败后的重新筛选、加入新候选后的恢复、连续失败的间隔重试、恢复后清除旧错误、429 等待头以及取消和配置变更保护。验证使用临时数据库、模拟模型与模拟 HTTP 响应，不依赖真实发帖或真实模型调用。

SDK 固定为 `capturethenarrative==0.5.1`。测试使用模拟模型和平台响应；没有凭据时不进行真实注册和发帖验收。

## 后续错误排查与经历记忆（2026-10-20）

上述记录为初次验收快照。用户随后为 Maya 选择了 `grok-4.7`。一次失败从模型请求到报错耗时 45.206 秒，吻合原模型客户端的 45 秒截止；原代码把超时、认证、额度、截断和 JSON 解析错误合并显示，无法从旧错误文本单独判断上游原因。

已分离模型调用与 JSON 解析的错误处理，保留客户端的安全原因和 HTTP 状态。Agent 的官方 xAI Grok 4 系列请求使用最多 120 秒时限，相应模型租约至少覆盖时限再加 30 秒；其他用途的默认时限保持 45 秒。请求不会自动重试，也不提高已配置的输出 token 上限。

用户明确允许一次复测后，Grok 在 86.703 秒返回了可解析的 JSON，但正文未通过文字/非空/500 字符领域校验，未创建待审动作。此结果证明等待超时与返回内容校验是两个不同问题。已为支持的 Grok 接口接入严格 JSON Schema，限制动作、来源、目标及 500 字符正文；仍做本地校验，失败分别报告字段类型、空正文或实际字符数。结构约束修改使用模拟响应验收，没有再调用云端模型。依据：[xAI 推理说明](https://docs.x.ai/developers/model-capabilities/text/reasoning)、[结构化输出与长度约束](https://docs.x.ai/developers/model-capabilities/text/structured-outputs)。

复测摘要保存在 `reports/generated/agent-grok-diagnostic.json`。经历记忆实际在 PostgreSQL 上接续并保留 15 条阅读经历、2 条账号往来线索；没有已完成平台操作被虚构。记忆验收见 `reports/generated/agent-memory-verification.json`。本次对照了 AI 分析、AI 配置迁移、分析缓存与容器排查会话，沿用已有云端连接、数据库和采集器；最终一次性重载服务。

最终 Agent 与模型客户端组合 118 项测试通过，Agent 页面 9 项测试及 TypeScript/生产构建通过。浏览器实际核对了 15 条已读经历和“实际做过的事”为零的状态；旧自述中的“已发帖/已回复”作为主观笔记保留，没有被当作已完成平台操作。服务与 PostgreSQL 健康检查通过。

## 发帖、账号分析与积分联动（2026-10-20）

角色绑定真实赛事账号后，账号公开资料进入既有账号表并标记为本队账号。确认成功的发帖、回复和转发在操作状态提交的同一短事务内进入既有帖子库，保存真实返回的帖子 ID、正文及关系。仅有 ID 的返回不会伪造正文、时间或互动数；点赞保存已确认操作关系，不自行增加目标计数。结果不确定时仍需核对，确认结果后走相同入库逻辑；持久回执避免重复确认、重复入库和重复安排任务。

模型上下文使用紧凑字段与共享来源片段，同一证据不再在多条笔记中重复展开。9500字符预算按相关性裁剪，为有内容的观点、疑问、人物印象等类别保留最相关条目，必要时缩短片段；不再按固定类别删光观点和疑问。完整归档不随本轮提示裁剪而改变。

角色编辑页将输入框明确为“手动补充的长期笔记”，自动观点、疑问、人物印象独立展示。“查找历史回忆”可按关键词和类型分页查看以前的经历及来源；接口为 `GET /api/agents/memory-history?agent_id=...&q=...&kind=all&limit=20&offset=0`，沿用工作台成员认证。`memory_view.long_term` 给出持久归档数量。

“清空记忆与阅读历史”会先将工作集和该角色归档保存到本地恢复文件，再清除归档、重置个人经历边界。操作审计及未完成队列仍保留用于核对，但不会恢复成旧个人回忆。Schema v8的便携备份、恢复与PostgreSQL迁移同时包含归档及来源索引。
