# 项目问题修复与性能优化（2026-10-20）

## 修复范围

| 问题 | 修复后的行为 |
| --- | --- |
| `-NoAutoCollect` 与数据库保存的开关不一致 | Worker 的任务领取与请求许可都读取当前调度器开关；启动时关闭采集不会覆盖用户保存的偏好。 |
| 数据库暂时不可用导致扩展缓存被隔离 | 后端标记错误是否可重试；扩展保留原记录 ID，对暂时失败及不确定结果持续重试，冷却时间持久保存。 |
| 不同精度、时区的时间字符串被错误排序 | 以精确到微秒的 UTC 索引键选择最新快照、排序历史与比较内容版本；历史原始时间和观测数据不改写。 |
| 单槽持久调度使部分帖子长期无法采样 | 直连与代理在成功、普通失败及 429 后均更新轮转状态，更新与租约完成保持同一事务。 |
| 保存分析漏掉 `sample_batch` | 页面查询、导出与保存复用同一参数构造，保留选定时间桶。 |
| Feed 403 被其他请求的 200 掩盖 | Feed 健康状态单独保存；Counter 成功不会覆盖 Feed 故障，429 仍遵守共享冷却。 |

## 性能改动

- 帖子列表批量读取引用帖和采集状态，避免每条记录重复查询。
- 运行页只读取需要的 Feed 与调度断点，不传输持续增长的观测收据；收据仍保留用于幂等。
- 采样规划通过按帖最新状态索引、范围查询和存在性检查访问快照；关闭计数采样时不扫描历史。窗口判断保留真实基线与端点要求。
- PostgreSQL 使用服务器游标分批读取分析、CSV 和备份数据；提前退出或异常时关闭游标，不提交调用方事务。
- 热门分析只保留有限的轨迹明细，同时保留全量统计和均匀抽样；前端使用实际观测与断点构建稀疏图表，缩放不重复计算基础轨迹。

### 同口径合成基准

以下是本机合成测试，不能直接等同于生产请求耗时。旧版与修复版使用相同数据及参数。

| 场景 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 200 条帖子的列表关联查询次数 | 1005 | 5 |
| 10000 帖、100 万快照的普通采样规划 | 4.1046 秒 | 0.1228 秒（约 33.4 倍） |
| 10 万条热门观测，返回 10 个轨迹点 | 13.446 秒 | 4.648 秒 |
| 上述热门轨迹的 Python 分配峰值 | 48.108 MiB | 0.007 MiB |

百万快照基准的窗口检查另耗时 0.0954 秒，且新旧普通规划选择结果一致。内存数值来自 `tracemalloc`，只代表该热门轨迹函数，不代表浏览器、数据库或整个分析服务。整体分析内存仍随选中帖子、词汇、关系和单帖最长历史增长。

## 数据库与发布

数据库结构版本升至 4，增加四个 UTC 时间表达式索引。初始化自动升级，原始记录与时间字符串保持不变。SQLite 和 PostgreSQL 都有对应时间函数及回归覆盖。

备份输出移除依赖自定义函数的四个可重建索引，可直接用普通 SQLite 工具检查和读写；恢复后由 CTN 初始化自动重建。真实 PostgreSQL 回归覆盖分批游标、时间解析、列表与覆盖统计、规划、分析、备份完整性及索引重建。

发布前已保存经完整性与外键检查的生产库备份，并保存原前端和扩展安装包。路径及发布验证记录位于 `reports/generated/project-fixes-deployment.json`。扩展源码与安装包版本为 1.3.1，已加载的 Chrome 扩展需要在扩展管理页重新加载一次。

本地服务已重启，健康检查确认结构版本 4 和四个新索引；前端入口及六个入口资源读取正常。自动采集开关与 60 秒间隔保持不变，两个 Docker Worker 心跳恢复，帖子、快照和 Feed 观测继续增长。发布后一次只读检查中，运行页从库内 33616 条断点/收据中仅返回 4 条需要的断点；200 条帖子列表约 0.59 秒、运行页查询约 1.64 秒。这是当时生产数据下的单次测量，受后台采集和数据库负载影响。
